# Backend v0.2.2 — hosted India catalogue

**Goal:** Make the verified India identity catalogue available through the existing Vercel backend, with explicit source age, partial coverage and reproducible build verification.

**Architecture:** Tracked compressed public source -> validated deployment build -> bundled read-only SQLite + artifact receipt -> existing separate catalogue lookup. Live OFF product/nutrition APIs keep their contracts and origins. A new catalogue status endpoint describes refresh dates and field limitations. A Git deployment replaces the immutable database; no bulk download or database write occurs in a request.

**Stack:** Existing Python 3.12/FastAPI/Pydantic/HTTPX, stdlib SQLite/gzip/hashlib and the existing Vercel FastAPI framework. No new database account, key, billing tier or mobile build.

## Scope and boundaries

- Backend becomes 0.2.2; frontend remains 0.0.0+1. Preserve historic contracts/tags and update active docs before every push.
- Serve the current 840,099-byte gzip projection: 21,188 rows, 21,138 indexed supported barcodes; coverage stays `unverified`.
- Investigate dated live/export differences with bounded source checks, and document unresolved causes. Do not force counts to match or call this every product sold in India.
- This release selects the current identity/ingredients/provider-grade fields. Nutrition tables, photos and per-product modification dates remain absent. Richer bulk-source acquisition is separate follow-up work.
- Existing `/v1/catalogue/products/{barcode}` remains snapshot-only: 200 found, 404 absent, 503 unavailable. No silent live fallback. Live routes remain online OFF3.6.
- Track a deployment receipt with actual SQLite bytes/hash and source metadata. Each build can differ in UUID/indexing time; reproducibility means validated source and content/counts, not identical SQLite file bytes.
- Age is calculated from source export time, never rebuild time. Manual refresh is due after nine calendar months. An overdue record remains explicitly dated; refresh is not a guarantee of ingredient/allergen accuracy.
- Plaintext env/private identities never enter cloud builds. Source/receipt/data are public OFF-derived facts with retained attribution/licenses.

## Deliverables and checks

1. **Public bundle builder:** Verify compressed/decoded lengths, hashes, 100 MiB budgets and expected source/counts before publishing a generated SQLite and receipt. Tests cover tampering, truncated gzip, inconsistent expectations and preserving existing output on rejected input.
2. **Hosted startup verification:** Hash the bundled SQLite once at startup, check receipt/manifest agreement and existing SQLite integrity/count checks. Invalid/missing receipt disables only catalogue features. Local editable runtime stores retain their existing explicit configuration.
3. **Status and freshness:** Add `GET /v1/catalogue` with typed ready/unavailable/not-configured status, manifest, artifact receipt summary, source age, nine-month due time and known field limits. Tests cover month ends, leap years, exact due boundary and future source dates. Expose current catalogue metadata additively in `/v1/meta`; preserve lookup schema v1.
4. **Actual coverage record:** Reproduce current export/index/missing-field metrics and compare a bounded live India count/product check with recorded source dates. Keep unexplained differences and unavailable columns visible. No per-barcode bulk crawl or new world download.
5. **Vercel build packaging:** Use a backend build hook, allow root public source/scripts at build time, and package only the generated owned data directory. Keep `.env*`, runtime stores and private/generated development files excluded. Verify build and database access on Vercel before considering hosted distribution complete.
6. **Nine-month replacement/rollback:** Document acquire -> validate candidate -> commit source/manifest -> automatic build -> verify deployment -> activate. Failed build leaves the prior deployment serving. Roll back to a previously verified deployment/source if needed; existing in-flight requests can finish on the earlier deployment. Do not write to a running serverless database.
7. **Release:** Export v0.2.2 OpenAPI/new status schemas and synthetic examples; prove strict existing product/nutrition/catalogue contracts unchanged. Run backend suite, lint/format/dependency/links/source review. Update README, clone/architecture/hosting/version/release/review docs, refresh age ciphertext if local settings change, then push main. Verify exact source deployments and public API/CORS/status/found/absent/invalid paths. Publish source-only backend v0.2.2 without dispatching APK/IPA builds.

## Completion gates

- Exact production source is READY; actual HTTPS catalogue lookup succeeds without an OFF request on the catalogue path.
- Status reports source hash/date, 21,138 records, artifact hash/size and refresh date; cloud catalogue missing/corrupt tests preserve other endpoints.
- Dated coverage limitations and request/fallback contract are documented for the Flutter teammate.
- SQLite is generated/excluded from Git; its committed source can restore a fresh clone. No keys/private scans or mobile version changes.
- Cold-start and repeated lookup timings are measured as observed samples, not a latency SLA or claim of offline phone support.
