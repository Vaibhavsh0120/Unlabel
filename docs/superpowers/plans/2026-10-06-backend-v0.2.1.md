# Backend v0.2.1 — India catalogue foundation

Historical release plan. Subsequent [recovery maintenance](../../planning/RECOVERABLE_WORKSPACE_REVIEW.md) keeps the compact public projection in Git and rebuilds SQLite locally; the original release boundaries below describe that earlier implementation step.

**Goal:** Acquire actual OFF India-market data and provide bounded, source-labelled SQLite import/lookup tooling without changing Flutter or the existing product/nutrition v1 contracts.

**Architecture:** Official export -> streamed exact `en:india` selection -> compact identity JSONL projection -> one read-only indexed SQLite file. Importing is a local maintenance operation. An optional separate catalogue endpoint preserves export provenance; existing live OFF endpoints remain available. CSV and JSONL are input formats; SQLite is the serving format. Firestore is unnecessary for a nine-month read-only product snapshot.

**Stack:** Existing Python/FastAPI/HTTPX/Pydantic backend; standard-library CSV/gzip/sqlite3, pytest/Ruff. No new paid service, API key, mobile rebuild or training.

**Evidence:** [Acquisition feasibility](../../research/INDIA_EXPORT_FEASIBILITY.md). India search reports 24,706 matches; filtered CSV failed. The official global CSV is reachable and its actual header was checked. User authorized large transfers on 6 October; stream the smaller CSV for identity lookup, rather than retaining the world dump. Nutrition aggregates are excluded. Full stream completion, coverage and deployment packaging still require evidence.

## Tasks and gates

1. Finish baseline files/docs review; preserve historical records and repair active status summaries. Correct the redacted 422 OpenAPI contract with a failing regression test.
2. Test source projection: exact country tags, literal quotes/backslashes, unknown fields, no nutrient/image leakage, schema changes and transfer bounds. Verify actual global export dialect before the full acquisition.
3. Stream the documented gzip CSV with EOF/checksum/byte-count evidence. Keep only India identity projection in ignored local storage. Record timestamps, counts and omissions; abort on schema/budget/truncation rather than silently drop records.
4. Build SQLite in a unique staging file, with an embedded manifest, source input hash, attribution, counts and exact barcode index. Bound rows, artifact (100 MiB) and work-directory (1 GiB); preserve leading zeros and unknowns. Fail duplicates and malformed input. Validate before atomic replacement; remove only invocation-owned staging files.
5. Add `/v1/catalogue/products/{barcode}` with its own snapshot provenance model. No upstream call or silent live fallback; 503 when inactive/corrupt, 404 when absent, 200 for indexed facts. Resolve trusted `.env` paths relative to backend. Keep live source API3.6 metadata out of export responses.
6. Verify real acquired India records, measured size and lookup latency. `coverage: unverified` means completeness of the market/independent dataset remains unproven even after a full source stream. Samples are marked `sample`. A future packaging/coverage milestone must pass before production snapshot preference is enabled.
7. Export v0.2.1 contracts, update README/API/folder/roadmap/storage/release/review docs, run meaningful checks and final independent file review, then commit/push. Verify both automatic deployments and public HTTPS API behavior. Publish a source-only backend release; frontend stays 0.0.0+1.

## Boundaries

No full corpus or SQLite file in Git, no image acquisition, no per-barcode corpus scraping, no automatic refresh schedule. CSV aggregate nutrition does not become direct package evidence. Local snapshot lookup does not make the mobile app offline. No claims/scoring/allergen-safety verdicts. FSSAI, glossary and comparison remain later versions. Nine-month replacement is manual, with old/new overlap bounded; product facts and regulatory evidence have independent freshness policies.
